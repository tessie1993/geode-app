# AGENTS.md: MuzViz Studio Pro (internal name Geode)

Android music player, reactive visualizer and video studio. Kotlin and Compose with Hilt, plus a C++20 native core (`libgeode.so`).
applicationId `com.muzviz.studiopro`. Kotlin packages stay `dev.geode.*`. minSdk 26, targetSdk 36, compileSdk 37.

## Where code lives (owner rule, no exceptions)

- **Kotlin runs on the main thread only:** Compose UI, ViewModels' UI state, and the thin Android glue that has to be Kotlin. That glue is Activity and Service lifecycle, Media3 session and player wiring, permissions, the MediaStore, MediaCodec and Transformer calls, billing IPC, and the widget, tile, wallpaper and dream shells.
- **Everything else is C++ in `core/`, behind `core/api/geode_api.h`, never Kotlin.** That means:
  - every worker, GL, audio and export thread
  - all logic and decisions
  - all audio code: DSP, the PCM ring, clocks, analysis
  - params: definitions, ranges, defaults, randomizing, clamping, modulation, routing
  - the catalogue, scheduling, export maths and timing
  - shaders, which `core/viz` drives
  - the engine's inner workings
- **Where:**
  - `core/sound`: hearing, analysis and the musical layer
  - `core/viz`: the renderer, scenes, params, Director, NoteResponse, Reactions, CameraRig, Catalogue and safety
  - `core/audio/dsp`: playback and export DSP
  - `core/studio`: the programme clock
  - ADR 0006's skeleton folders: the target shape
  - `app/src/main/cpp/*_jni.cpp`: only marshals values
- **Why:**
  - One engine serves live, export, wallpaper and dream, so they can't drift apart.
  - It is deterministic and testable on the host in `core/tests`.
  - There are no GC pauses or chatty JNI calls on real-time threads.
  - There is one source of truth instead of a Kotlin copy and a C++ copy.
  - See [ADR 0003](docs/adr/0003-engine-internals-in-cpp.md) and [ADR 0006](docs/adr/0006-fosfora-aligned-engine.md).
- **When a change touches logic that is still in Kotlin,** put the new logic in C++ and leave Kotlin as a thin caller. Never add logic to Kotlin. The leftovers are listed under "Where the code breaks the architecture guide".
- **Never build, compile or lint in an agent container,** and never run Gradle, the APK build or the emulator. Push to `claude/**` and let GitHub CI do it. The one exception: before every push, run `python3 tools/precheck.py` (about 20 s). It checks for conflict markers and brace balance, runs the three gates, and runs the native host tests the branch touches, taken from `android.yml`.

`LiquidPass` is a full-resolution feedback ping-pong between the scene target and the composite that advects the last frame by the `FlowField` velocity, zooms and twists about the vanishing point for the dive, and re-pours the style through `liquid_frag`), `compute/`; per frame the renderer runs `Director` (the auto-director: the feeling decides palette, macro knobs, camera moves and routes at sections and drops, under the user's settings) → `NoteResponse` (Note & key reactions: notes, chords, key and mood inside the director's look: a colour per note, interval motion, tension distortion, chord-change fold shifts, the six style knobs, drums weighted by measured percussiveness, and a tint toward the notes' colour in `composite_frag`; a personality rolled at random per play and section; `docs/research/note-key-response.md`) → LFO → ADSR → `Reactions` (the reaction matrix) → `MotionField` → `safety::apply`, then after the composite `OutputProbe` measures the finished frame (an async 16 × 16 readback) for `FlashLimiter`, the photosensitive flash limit (WCAG: at most three flashes a second), which holds the next frames toward one grey through the composite while the picture would flash (it also counts the envelopes' and LFOs' luminance modulation, `FlashLimiter::drive`, so those strobes hold at once), in an export also steps `StyleSchedule` (the segment's style switches, by time and by beat), then steps `CameraRig`, the one camera every render path shares, which also reads the sound frame for its own cuts, trauma shake and clock-driven orbit), `core/audio/dsp` (playback DSP: `DspProcessor` keeps a chain per format, staged at configure and live at flush, so a draining tail never meets the next format's chain; plus the export resampler `PcmResampler` and BS.1770 meter `Loudness`) and `core/library` (TagLib, and `Search`: which tracks a voice "play X" plays, `geode_library_search`). The submodules are `third_party/{projectm,taglib}`. Playback is ExoPlayer only; the native player (`core/audio/player`, Oboe) is gone. projectM gets `tools/projectm-v4.1.7-render-fbo-backport.patch` at configure time. Shaders ship in `app/src/main/assets/shaders/`; styles include `lib_*` files by `//#include`, allow-listed in `core/viz/ShaderIncludes.inc` (`ShaderSource.cpp` compiles it in; `tools/check_shaders.py` and `tools/glslcheck` read it). 3D styles read the rig through `lib_camera`, every style hears sound through `lib_sound` (pasted by `lib_scene_uniforms`; scenes upload it with `core/viz/SoundUniforms`). Endless zoom is `core/viz/EndlessZoom.hpp`: two layers an octave apart, crossfaded so the dive loops without a pop, pushed by the bass (`bassAtt`) and drifting slowly in silence; 2D styles draw them through `lib_zoom` (pasted by `lib_scene_uniforms`; it runs the style's `main()` a second time only inside the crossfade window), MilkDrop's post pass samples them, and 3D styles dive by flying `CameraRig` instead. In Liquid mode (`SceneParams.flowEnabled`, Customize › Advanced › Liquid; Liquidity, Push, Swirl and Dive are `flowStrength`, `flowForce`, `flowCurl`, `endlessZoomSpeed`, also LFO targets) 2D styles' `lib_zoom` layers step aside for `LiquidPass`, 3D styles still fly `CameraRig`, touch moves the liquid instead of drawing ripple strokes, and a hot phone follows Settings › Performance. Glass and Truchet stay on the old law until their redo (`endless::keepsTriangle`). A style's six knobs are `uKnob[6]` in `lib_scene_uniforms` (k0 PULSE … k5 SPACE); `ShaderScene::uploadParams` takes them from `NoteResponse` (exactly 0.5 while it is off). The neon set (`glow_vortex`, `neon_chrome_sea`, `black_hole`, `hex_hive`, `mandelbox_cathedral`) shares `lib_neon`: each spends Morph, Warp, Turbulence and Intensity on its own geometry through normalized reads, so Customize, macros and DNA reach it, and adds each style knob's offset from 0.5 on top. The simulation scenes (Silk, Fluid, Life, Acid, Cymatics) present their field as a lit 3D surface through `lib_relief` (parallax, a sound-driven light and tilt, eight material looks taken from the families). A style family's twelve styles (`arbor_*`, `bulb_*`, `chrys_*`, `lucid_*`, `dive_*`, `glass_*`, `nebula_*`, `terra_*`, `truchet_*`, `foam_*`) share `lib_<family>` and are listed in `core/viz/Catalogue.cpp`. The UI blur (`core/viz/UiBlurPass`, `ui_blur_frag` and `ui_blur_mask_frag`) frosts the live visual under the app's glass sheet after the composite: a rounded rect set by `VisualizerView.setUiBlurRegion` (0..1, y down; `geode_viz_set_ui_blur_region`), blurred at quarter resolution, free at strength 0 and never drawn offscreen.

## Data flow and threads

1. **Source → `SampleRing`.** ExoPlayer runs `MvzAudioProcessorChain` on its playback thread, and the `PcmTap` there comes first, before any DSP. `NativeDspProcessor` sits after the tap and steps aside (inactive, not throwing) for formats its chain cannot run, such as 5.1 files. Mic and capture use one `AudioCapturePump` worker thread each. All three write through one `PcmSink` (`PlaybackSession.captureSink`) into two rings: `SampleRing` (stereo, what every sound engine hears) and `PcmRingBuffer` (a mono mix, which `PlayerSession.latestPcm` hands to the in-app renderer's `pushPcm` for the scenes that take raw PCM).
2. **Sound input.** `PlaybackSession.soundInput` is `SampleRing` plus `sampleRateHz`, which the tap's format sets, or `CaptureController` while the mic or another app's audio owns the ring; it is published as `AudioBus.soundInput`. There is no analysis thread: every renderer's own `core/sound` engine hears the ring on its GL thread.
3. **Render.** The `GLSurfaceView` GL thread runs `VisualizerRenderer.onDrawFrame`, which calls `NativeViz`, then JNI `geode_viz_jni.cpp`, then the `core/viz` renderer and its scene. Built scenes stay resident only while `core/viz/SceneResidency.hpp` allows (the ones drawn plus a few recent spares, fewer as the phone heats; a spare is resized when drawn again). A new scene is built across frames, never in one (`core/viz/ScenePrep.hpp`, `ProgramStager`: a bounded slice of program compiles per frame, polled through `GL_KHR_parallel_shader_compile` where the driver has it, while the old scene keeps drawing), so a main-thread call that waits on the GL thread never waits out a whole build; an export (`geode_viz_set_offscreen`) builds each scene whole on its first frame. Reaction routes are the user's (`LfoStore`, with Customize › Music's hand mask beside them: the user's routes play only on the moments they set, the live DNA on the rest, and the director keeps off those moments; `hand::` in `core/viz/Reactions`, `mergeHand` and the Music page's edits in `core/viz/ReactionDna`, pushed process-wide as `HandMask`) or the style's DNA, built natively by `core/viz/ReactionDna` (a personality for each side of the groove plus layers, each drawing its source from the sound frame) over the 117 `ReactSource`s, one per `GeodeSoundFrame` value and fetched through `BuildStyleReactionsUseCase` (`geode_style_reactions`), resolved on the GL thread by `StyleReactionsCache`; `OffscreenSceneRenderer` resolves them the same way, so exports react like the screen. `GyroLook` (in `VisualizerView`) feeds the camera's look while it is visible. Each frame the GL thread also writes the ring's new PCM (`AudioBus.soundInput`) into the native renderer's own `core/sound` engine, which `beginFrame` steps with that frame's dt (the musical layer's rhythm hops inside `write`, so beats depend on the samples, not the frame rate); styles read it through `lib_sound` (`uSound`, `uSoundTex`, `sndChroma`). Auto is one mode: each new section or drop the director commits a look at is counted natively (`geode_viz_take_director_style_moments`), and `VisualizerRenderer.onDirectorStyleMoment` hands it to `AutoVisualsController.onDirectorMoment`, which steps the visual playlist or draws a new style from Auto's sources. The wallpaper and dream read the same `AudioBus.soundInput`.
4. **Export.** `VideoExporter` and `LoopRender` run on Default inside `ExportRun.scope`. They render through `OffscreenSceneRenderer`, whose own sound engine hears the track frame by frame (`TrackAudio`, stepped at 1/fps, so export equals live); a take's style switches and a clip's beat cut reach it as one `StyleSchedule` per segment (`geode_viz_set_style_schedule`), which `core/viz/StyleSchedule` times on the render clock and that engine's beat count, and `EncoderSurface` (EGL on the export thread) into MediaCodec and MediaMuxer, and write MediaStore rows with `IS_PENDING` set. `StudioExporter` uses Media3 `Transformer`. One render path (#232): every render is a project. `ProjectComposition.plan` says how each clip renders (footage, offscreen scene, caption, mix, or skipped with a reason) and `ExportController.render` runs it under `ExportRun` + `ExportService`: one visual over one song (the one-tap Render) goes straight through `VideoExporter`; anything else draws each scene segment to a `studio-` scratch MP4 and `ProjectComposition.compose` layers them for `Transformer`. `ExportController.renderProject` is the Studio entry point; the skipped-clip report is `StudioUiState.notice` and a toast.
5. **Persistence.** `PlayerSession.storeScope` is `Dispatchers.IO.limitedParallelism(1)`.

## Conventions

- ktlint and detekt are baselined (`config/detekt/detekt.yml`), so new code must pass them clean.
- KDoc explains *why*, at length. Match the density of the file you're in.
- Use `bestEffort(TAG, "what")` (`dev.geode.util`) for best-effort failures. Failures go to `RingLog`.
- Scratch files use the prefixes `geode_aac_`, `geode_loop_` and `studio-`; `GeodeContainer` sweeps them. Renders insert with `IS_PENDING`.
- The tap stays first in the audio chain, and the chain never gets float output (see `docs/AUDIO_CHAIN.md`).
- Cast to TV is the app's only internet use (`INTERNET`, `ACCESS_NETWORK_STATE`; CI fails if INTERNET appears without `CastService`, if a socket or HTTP API is used outside `cast/`, if a networking, analytics or ads SDK joins the release build, or if AD_ID appears). Everything else is offline; Play Billing works over IPC to the Play Store app.
- Runtime permissions are asked for in context through `ui/PermissionRequest.kt` (`rememberPermissionRequest`: rationale first, retry after a refusal, app Settings once Android stops asking). First run is the safety notice alone (`SafetyConsent` on `OnboardingScaffold`; `FirstRunGate` passes straight through). Music access is asked the first time Library opens.

## Where the code breaks the architecture guide

- **God object.** Every ViewModel reads `PlayerSession`, which builds 16 controllers and its repositories by hand. That's a service locator (`GeodeContainer`, `context.geodeContainer`) sitting beside Hilt.
- **Layer rule (enforced).** Nothing outside `ui/` and `di/` may name `dev.geode.ui`; `tools/layer-gate.sh` fails the PR otherwise. Move a type down instead: `model` if it is pure, `data` if it touches storage.
- **Engine Kotlin only shrinks (enforced).** `tools/engine-kotlin-gate.sh` fails a PR whose net Kotlin lines grow under `engine/*/src/main/`, `export/` or `audio/dsp/` (only `GeodeNative.kt` and `NativeViz.kt`, the JNI declarations, are exempt). Write the logic in `core/` and call it through `geode_api.h`.
- **Data layer lives in `ui`.** Stores and MediaStore access (`*Controller`, `VizStateStore`, `AutoVisualsPrefsStore`) sit there, and some composables call `contentResolver` themselves (`MyVideosTab` (thumbnails), `TrackInfoEditor`, `DuplicatesTab`, `FolderSettings`, `LoopRenderSheet`).
- **One-shot events.** `PlayerViewModel` exposes `vizApply` and `morphFade` as `SharedFlow`.
- **Engine logic in Kotlin (ADR 0003).** Engine internals belong in `core/`; GLOSSARY › Code has the words. Native already runs the touch field, the flash clamp, the cymatics plate, the export resampler and the BS.1770 loudness meter (their Kotlin copies are gone). Still Kotlin: the scene and style catalogue, `ParamRandomizer`, the PCM ring and presentation clock; the ADR's table gives each one's target and blocker.
- **Mixed module.** `:engine:scenes` is an Android library, but most of its files are pure Kotlin. `editor/*` and much of `data/*` are pure too, except for `org.json` (`TemplateFormat`, `EditorProjectJson`, `PerformanceTake`). There is no `kotlinx.serialization` yet.
- **Navigation.** Enum and `when` at the top level; only the Visuals panel runs on Nav3 so far.
- **Quality items not set up:** two use cases so far (`pro/GetFeatureGateUseCase`, `render/scene/BuildStyleReactionsUseCase`), almost no ViewModel or repository tests, a hand-written (not generated) baseline profile (`app/src/main/baseline-prof.txt`), no `reportFullyDrawn`, JankStats, Macrobenchmark or GWP-ASan.
